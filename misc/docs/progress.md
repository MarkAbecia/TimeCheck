## Phase 4 — Auth end to end (done, 2026-11-24)

**Supabase (local)**
- Asymmetric ES256 signing keys (`signing_keys.json`, gitignored), so the API validates local tokens through JWKS just like production.
- `site_url` is :3400. The recovery email template links to `/auth/confirm?token_hash=…`.

**Backend**
- Onboarding gate, enforced server-side. Every policy except `SignedIn` requires no pending password change and the current privacy-consent version.
- After any password change the BFF revokes the user's other sessions (GoTrue `logout?scope=others`); verified with two devices.
- `POST /me/password`: the API sets the password through the Supabase admin API (`IAuthAdmin`), clears `must_change_password` and audits the change. The password never reaches the audit log.
- `POST /me/privacy-consent`: the version must match `Auth:PrivacyConsentVersion`; stores the version and timestamp and audits it.
- `/me` now also returns the required consent version, whether MFA is required, the church name and the group name.
- The secret key comes from user-secrets or env (`Auth:ServiceRoleKey`), never from the repo.

**BFF (Next.js route handlers)**
- Login, logout, forgot-password, password, consent, MFA enrol and MFA verify, plus `/auth/confirm` for reset links.
- Tokens live only in httpOnly cookies. Every POST checks the same origin. Rate limits are in Redis, falling back to in-memory.
- Forgot-password always answers 204, so it never reveals whether an account exists.
- `proxy.ts` is now the auth gate: silent token refresh, a redirect to `/login?next=…` when signed out, and `Cache-Control: private, no-store` on pages.

**Screens**
- The app shell uses the real session (name, role band, group, church).
- Signed-in users are routed through `/change-password`, then `/mfa` (admins), then `/consent`, before the app opens.
- `/reset-password` requires the recovery session. An expired link lands on forgot-password with an explanation.
- Sign-out is a no-JS form POST: an icon beside the theme toggle on the sidebar and the phone app bar, and a "Not you? Sign out" link on each onboarding step.

**Verified**

- Backend: domain (16), application (7), architecture (5) and integration (**25 of 25**) tests all pass, including the new onboarding tests. The other-church fixture was updated for the onboarding gate.
- Live against local Supabase:

## Phase 6 — Events & attendance (done, 2026-11-24)

Defaults taken from the open questions (§15):
- Leaders mark attendance (Q2).
- Week of Fire and Cell Celebration are one church-wide event each, with the roster split by group (Q3).
- Morning Prayer is created per group, Monday to Saturday.
- Leaders can edit marks for 7 days (church setting `attendanceEditWindowDays`); after that only admins can.
- Unmarked counts as absent in rates. Excused doesn't count either way.

Built:
- **Generator (`EventGenerator`, Worker):** a Hangfire recurring job at 00:10 Manila, also triggered on start-up. It creates the next 14 days of events for types with a fixed cadence (per group or church-wide) and skips occurrences that already exist. It runs across churches with explicit `church_id` filters, because there is no HTTP tenant in the Worker.
- **Scheduling:**
  - Event types list; events by date range (62 days at most; filter by group, type and category; cancelled on request); `/me/today`.
  - Create: leaders schedule their own group's leader types, admins schedule anything. Only Cell Meetings repeat (1–26 weeks), each at the same local time. A clash with the group's other events is a 409 `event.conflict` warning the user can confirm.
  - Edit and cancel notify everyone expected. Edit notifies only when the time changes.
  - Every write is audited.
- **Attendance:**
  - `PUT /events/{id}/attendance` takes bulk marks (up to 1000) and skips unchanged ones, so a retry is harmless. A stale `rowVersion` is a 409 `stale`.
  - Future events are 422. Marking past the edit window is 403, except for admins. Leaders can mark only their own group.
  - Audits record the before and after status. Note text is not recorded, only whether there is one.
- **History:** `/me/attendance` returns the last 30 days (up to 92), the rate, and the Morning Prayer streak.
- **Screens:**
  - Today now runs on real data, with a banner for past events still waiting on marks.
  - `/events`: an agenda by week, a "Needs marks" view, and group and kind filters for admins.
  - `/events/new` and `/events/[id]/edit`: the schedule form, with the clash step.
  - `/events/[id]`: details, edit, a two-tap cancel, and your own status. For markers it shows the attendance sheet: "Mark all present", tap the exceptions, save. Admins can pick a group chip on church-wide events.
  - `/history`.
- **Offline:** marks saved without a signal (or on a 5xx) are queued in `localStorage` and sent on load or when the connection returns. Clashes are reported and dropped. Signing out clears the queue, so a shared phone never sends the last person's marks.
- **Also fixed:**
  - Audit JSON now stores enums as names. Role and status audits were storing numbers.
  - A unique-index violation now maps to 409 `stale` instead of 500.
  - Sonner's light toasts used colours under 4.5:1; they now use the app's status tokens.

## Phase 7 — Devotions & AI detection (done, 2026-11-24)

Defaults taken from the open questions (§15):
- No detection provider is chosen yet (Q6); see ADR 0006. Production runs with `Ai:Provider=none`, so devotions are saved and shown as "Not checked". Development uses a fake detector (`Ai:Provider=fake`, allowed only with `Ai:FakeAllowed`) that scores from the content hash.
- Slot windows: Day 00:00–23:59, Night 18:00–05:00 the next day, both inclusive of the closing minute (church settings `devotions.*`).
- Bands: under 40 likely human, over 75 likely AI, uncertain between (church settings). Members don't see their own score unless `membersSeeOwnScore` is on.

Built:
- **Submit:** `PUT /me/devotions/{date}/{slot}` takes multipart text (up to 5000 characters) and/or a photo (10 MB max, JPEG, PNG or WebP by magic bytes).
  - SkiaSharp corrects the orientation, caps the long side at 2048 px and re-encodes to JPEG 85, which strips EXIF, GPS and anything appended.
  - Photos go to the private `devotions` bucket in Supabase Storage at `{church}/{user}/{sha256}.jpg`. A failed save deletes the upload; a replaced photo is deleted after commit.
  - Submitting again edits the devotion, never duplicates it. A closed slot is 422 `devotion.closed`. The audit records only whether there was text and a photo.
  - The BFF forwards only this one multipart route, checks its size, and gives it 30 s.
- **Detection (`DevotionChecker`, Worker, every minute):** batches of 50 pending devotions. A content hash already scored in the church reuses its score. Church `ai.enabled` off or no provider gives SKIPPED. After an hour a devotion is FAILED, and 3 provider errors in a row stop the batch. The content hash is a concurrency token, so a score is never written onto edited content.
- **Reminders (`DevotionReminders`, Worker, every 15 minutes):** after the church's reminder time, while the slot is open and nothing is submitted, one `devotion.reminder.day` / `.night` outbox row per person per slot per day.
- **Review:** leaders see their groups' members for a day (`GET /devotions`, with a likely-AI filter), open one (`GET /devotions/{id}`, a 5-minute signed photo URL) and mark it reviewed with a private note. Admins see everyone. Anything out of reach is 404.
- **Screens:**
  - `/devotions`: the streak, a card per open slot (type, take a photo or choose one, send: three taps), and the last 30 days. The photo is shrunk to JPEG on the phone before upload.
  - `/devotions/group`: day navigation, the likely-AI filter, group chips for admins, and the fairness disclaimer wherever scores are shown.
  - `/devotions/[id]`: the text, the photo, the band with text and photo %, and the review form.
- **Also fixed:** role checks written as `me.Role >= UserRole.ADMIN` were true for everyone, because the enum starts at SUPER_ADMIN. They now use `IsAdmin()`. The integration tests caught it before it shipped.

Frontend typecheck, lint, 49 unit tests and the production build pass.

## Phase 8 — Invites (done, 2026-11-24)

Defaults taken from §6.5 and the open questions:
- Guests are logged for a Cell Meeting or Cell Celebration the member can see, from 7 days before today to 30 days ahead.
- The member or their leader marks "Came" or "Didn't come" once the event has started. Either can switch it back.
- Guests have no account, so when an event is cancelled their inviters are told instead (`invite.event_cancelled`), to pass it on.
- Unconverted guests are erased 90 days after the event (church setting `invites.purgeAfterDays`).

Built:
- **API:**
  - `GET /me/invites`: your guests from the last 60 days onwards, and the events you can invite to.
  - `POST /invites`, `PATCH /invites/{id}`, `PUT /invites/{id}/status`, `DELETE /invites/{id}`.
  - `GET /invites` (leaders): their groups' guests by event or date range (92 days at most). Admins see everyone.
  - Only the inviter, their leader and admins reach an invite; anyone else gets 404. Guest contact is encrypted at rest. Audits record status changes and whether a contact was given, never the name or contact.
- **Converting:** registering a member takes an optional `inviteId`. The leader's "Register as member" opens the usual form with the guest's name filled in, and saving links the invite to the new member. A converted invite can't be changed or removed after that.
- **Removing:** a mistaken invite is erased (name replaced, contact cleared, hidden), not deleted.
- **Worker:**
  - `invite-reminders`, hourly: "Did your guest come?" to members with guests still expected at an event that ended 2 hours to 3 days ago. At most once per person per day.
  - `purge-invites`, nightly at 02:30 Manila: erases unconverted guests past their purge date.
- **Screen `/invites`:** add a guest (event, name, optional contact) with the privacy note; your guests with Came / Didn't come and a two-tap remove. Leaders also see their group's guests, with who invited them and "Register as member".

Checked:

## Phase 10 — Reports (done, 2026-11-25)

Decisions are in ADR 0008: one plain SQL view for attendance, a per-church Redis cache, hand-written export files.

Built:
- **Database:** view `attendance_facts` (one row per person expected at a started, uncancelled event, with their group that day and their status, `UNMARKED` if nobody marked them) and indexes for reports and export jobs.
- **API (`/reports`, leaders and up):**
  - `GET /reports` lists the reports the caller can run. `GET /reports/{type}` runs one with `from`, `to`, `groupId`, `eventTypeId` or `category` (up to 366 days).

Added while waiting on accounts (§6.10, 2026-11-25):
- **Member search** (admins): a search box on Members (`GET /members?q=`), a plain GET form with no client JS. Matches part of a
