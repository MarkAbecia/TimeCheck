# 0002 — Authentication approach

Status: Accepted (2026-11-24)

## Decision
- Supabase Auth issues JWTs (asymmetric signing keys; validated in the API via the project JWKS: issuer, audience `authenticated`, expiry, signature).
- Browser never sees tokens. Next.js BFF route handlers sign in with Supabase, store access + refresh tokens in `httpOnly; Secure; SameSite=Lax` cookies, and forward `Authorization: Bearer` to the API server-side.
- Role, church and group membership are loaded from `app_users` by `auth_user_id` (Redis cache ≤ 60 s, invalidated on role change). JWT claims beyond `sub` are not trusted.
- Deny by default: a global fallback policy requires an authenticated user that exists in `app_users` and is not deactivated. Only health endpoints are anonymous (architecture test).
- Public sign-up is disabled. Users are created by the API through the Supabase Admin API (service role key in backend/worker env only).
- MFA (TOTP) is required for Admin and Super Admin: the API rejects admin-policy requests whose token `aal` is not `aal2`.

## Consequences
- One DB/cache lookup per request for the current user; cached to keep p95 low.
- Role changes take effect within 60 s at most, immediately when the cache entry is invalidated.

## Phase 4 additions (2026-11-24)
- **BFF keys.** The web service talks to Supabase Auth with the *publishable* key only. The secret key (`Auth:ServiceRoleKey`) lives in the API/worker environment (user-secrets locally) and is used only for the admin API.
- **Session cookies.** `tc_at` (access, max-age = token lifetime) and `tc_rt` (refresh, 30 days). `proxy.ts` refreshes a stale access token before the page renders, so expired sessions refresh silently. Logout calls GoTrue `/logout?scope=local`, which revokes that refresh token.
- **CSRF.** Cookies are `SameSite=Lax`, and every BFF POST also requires `Origin` to equal `APP_URL`.
- **Rate limits.** Login, forgot-password, password change and MFA verify are limited in Redis (fixed window, hashed keys). Without `REDIS_URL` the limiter falls back to in-memory; if Redis is down it fails open.
- **Password reset.** The email links to `/auth/confirm?token_hash=…&type=recovery`. The BFF verifies the hash server-side and sets the session cookie, so no token appears in the URL fragment or in JS.
- **Password changes** (forced first-login change and reset) go through the API, which sets the password via the admin API, clears `must_change_password` and writes an audit row. Users never call GoTrue `/user` for this. Afterwards the BFF revokes the user's other sessions, so a new password locks out other devices.
- **Onboarding gate.** The API enforces it: every policy except `SignedIn` (used by `/me`, `/me/password`, `/me/privacy-consent`) requires that no password change is owed and that the stored privacy-consent version equals `Auth:PrivacyConsentVersion`. The web app only routes users to the step they owe: change password, then MFA (admins), then consent.
- **MFA enrolment** goes through BFF routes (list factors, enrol TOTP, challenge, verify). A verified challenge replaces the session cookies with an `aal2` session.
